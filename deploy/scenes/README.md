# Сцены отказа

Скрипты для ролика и для замера. Каждый печатает ход событий с отметками времени и пишет итоги в `runs/`. Вывод в терминал и сводки по-английски: они идут в кадр, ролик на английском (решение владельца 19.11). Комментарии и документация по-русски. Написаны 19.11 без стенда, в тот же вечер прогнаны на пересобранном стенде (scene-a, outage-writes, two-off, infected-pod); у пользователя ошибок 0 во всех четырёх, правки по итогам прогонов вошли в код. Задержку тревог Falco сцена «заражённый под» считает по меткам журнала контейнера (`kubectl logs --timestamps`), а не по полю `time` самого Falco: оно после подводки часов машины уезжает (19.11 на +0,48 с).

| Скрипт | Что делает |
|---|---|
| `scene-a.sh [machine-2]` | нагрузка через вход, машина выключается на `OFF` секунд и возвращается; ловит момент, когда кластер признал машину мёртвой и когда поиск снова в трёх копиях; в конце ошибки у пользователя и сколько было бы без повтора |
| `return.sh [машины…]` | возвращение: включить, дождаться узла и пира Qdrant, дождаться, пока копии шардов Active и совпадают (`replicas.py`), разложить поиск обратно по машинам |
| `outage-writes.sh [machine-2]` | записи в отдельную коллекцию `outage_rf2`, пока машина выключена и возвращается; потом сверка копий и проверка, что каждая подтверждённая запись на месте |
| `two-off.sh` | схема RF3: выключены две машины из трёх; поиск читает свою полную копию через `qdrant-local`; у Kubernetes в это время нет кворума |
| `infected-pod.sh [machine-2]` | атакующий с оболочкой в поде поиска под нагрузкой: попытки изнутри (`attack_pod.py`: интернет, DNS, API Kubernetes, соседи, Мак, стереть и записать базу ключом пода), тревоги Falco той же машины, карантин (с пода снимается метка `app=search`, остаётся только default-deny), чистый под, удаление заражённого; итог `infected_summary.py`: что отбито, через сколько первая тревога, ошибки у пользователя |
| `load.sh start [RATE]`, `load.sh stop FILE` | генератор `panel/loadgen.py` на machine-4 с проверкой TLS по УЦ стенда; снимок раз в 0,5 с в `/run/stand-load/load.json`, его показывает панель (`deploy/panel`); итог печатает `load_summary.py` |

Что настроено для быстрого отказа:

- `deploy/k3s/failover-tuning.sh`: узел признаётся мёртвым через 25 с вместо 50 с по умолчанию (`node-monitor-grace-period`), таймауты HTTP/2 у kubelet сокращены до 10 + 5 с, как требует документация Kubernetes для такого срока. Применяется по одной машине, без потери кворума.
- Сервис поиска сначала идёт в пир Qdrant на своей машине (`deploy/qdrant/local-svc.yaml`, `internalTrafficPolicy: Local`), общий сервис запасной; соединение к пиру ждём 0,1 с.
- Поды поиска уходят с мёртвой машины через 30 с после признания (`tolerations` в `deploy/search/k8s.yaml`).
