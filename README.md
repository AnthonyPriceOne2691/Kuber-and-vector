# Kubernetes и Qdrant. Поиск по договорам на трёх машинах

Сервис ищет ответ в договорах и возвращает его с адресом источника, то есть с документом, разделом и номерами
символов. Под ним векторная база Qdrant из трёх пиров на кластере k3s с тремя управляющими узлами. Четвёртая
машина держит вход, генератор нагрузки, панель и мониторинг. Все четыре машины это виртуальные машины Lima на
одном ноутбуке (Apple M5, 32 ГБ), поэтому числа ниже про это железо.

Документация и комментарии в коде по-русски. Всё, что идёт в кадр ролика, по-английски.

Качество держат два приёма. Название документа и раздел стоят в начале каждого куска, это поднимает recall@64
с 51,8 % у простых кусков до 82,6 %. Сервис сначала выбирает договор, названный в вопросе, и ищет уже внутри
него, это даёт 89,4 %. Сцены пишут сырые итоги в `runs/`, эта папка в git не входит.

## Как устроено

| Папка | Что внутри |
|---|---|
| `app` | сервис поиска на FastAPI. Вопрос делится по первой точке с запятой на ссылку на договор и сам вопрос, договор выбирается по коллекции названий, куски ищутся внутри него. Если договора нет в базе, сервис отказывает без поиска и без модели. Ответ модели со ссылками и проверкой цитат в `app/answer.py` |
| `deploy/vm` | одна схема для четырёх машин, песочница и комплект пакетов без интернета, суммы и подписи сверяются (`deploy/vm/signatures.md`) |
| `deploy/k3s` | k3s с тремя серверами etcd, быстрое признание мёртвого узла, правки по kube-bench, DNS кластера без выхода наружу, политика «только образы из комплекта» |
| `deploy/qdrant` | три пира Qdrant, коллекции RF2 и RF3, реестр моделей векторов и шлюз только на чтение для панели и мониторинга |
| `deploy/search` | образ сервиса, собранный без интернета, три реплики |
| `deploy/observer` | вход на machine-4, HAProxy с TLS и ключом API |
| `deploy/host` | фильтр Ollama на Маке, машины получают через него только векторизацию двумя моделями и чат модели ответа |
| `deploy/falco` | правила Falco, тревоги идут в панель |
| `deploy/monitoring`, `deploy/panel` | Prometheus и Grafana, панель стенда |
| `deploy/scenes` | сцены отказа машины, двух машин из трёх, смены модели и заражённого пода |
| `deploy/security` | скан снаружи, trivy и kube-bench |
| `deploy/limit` | предел стенда на синтетике, итоги в `eval/results/limit.md` |
| `eval` | замеры качества, итоги в `eval/results` |
| `panel` | панель стенда и генератор нагрузки |
| `showcase` | страница поиска с разметкой юристов и доска чисел |
| `docs/security` | модель угроз со статусами мер (`threat-model.md`) |

## Как поднять

Нужно заранее. macOS на Apple Silicon, Lima и socket_vmnet (`deploy/vm/README.md`), комплекты `kit/vm`, Falco и
мониторинга (`deploy/vm/kit-build.sh`), Ollama на Маке с bge-m3 и snowflake-arctic-embed2, подготовленные куски
(`python3 -I eval/prepare.py`).

```bash
QUIET=1 deploy/stand-up.sh        # стенд с нуля, около семи минут
deploy/check.sh                   # проверки стенда
deploy/scenes/scene-a.sh          # машина выключается под нагрузкой и возвращается
deploy/scenes/two-off.sh          # две машины из трёх
deploy/scenes/model-switch.sh     # смена модели векторов
deploy/security/scan-ports.sh     # скан снаружи
deploy/scenes/infected-pod.sh     # оболочка у атакующего внутри пода поиска
python3 -I -B showcase/server.py  # страница поиска на 127.0.0.1:8095, доска на /board
```

Панель стенда открывается на Маке по адресу http://127.0.0.1:18090. Скрипты `deploy/stand-stop.sh` и
`deploy/stand-start.sh` останавливают стенд без удаления машин и поднимают снова, на стенде они ещё не прогонялись.

## Проверки

```bash
python3 -I -B -m unittest discover -s tests -t .              # 361 тест
python3 -I -B -m unittest discover -s panel/tests -t panel    # 130 тестов панели
```

CI на каждый push гоняет эти тесты, `bash -n` и shellcheck по скриптам, helm lint чартов Qdrant и Falco,
kubeconform против схем Kubernetes 1.37.2 и kube-linter (`.github/workflows/ci.yml`).
