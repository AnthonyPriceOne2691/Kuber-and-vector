# Модель угроз стенда

Стенд стоит на одном ноутбуке, но защищается так, будто его машины видны из интернета. Здесь перечислено, что защищаем, от кого, чем, как это проверено и что остаётся открытым. Статус у каждой меры один из трёх. «Проверено» значит, что мера прогнана на живом стенде, дата указана. «Написано» значит, что код есть, но на стенде он ещё не запускался. «План» значит, что мера только запланирована.

Состояние на 19.11.2026.

## Что защищаем

| Ценность | Где живёт |
|---|---|
| Тексты договоров и их векторы | Qdrant на machine-1…3, по копиям шардов |
| Ключи Qdrant: админский и только на чтение | Secret `qdrant-keys`; у сервиса поиска только ключ на чтение |
| Ключ API входа | `/etc/haproxy/api-keys.map` на machine-4 и копия демо-клиента в `runs/` на Маке |
| Ключ УЦ стенда | `/etc/haproxy/certs` на machine-4, наружу уходит только открытый сертификат |
| Токен и сертификаты k3s | `/var/lib/rancher/k3s` на серверах кластера |
| Токены панели: Kubernetes только на чтение и токен событий | `/etc/stand-panel` на machine-4, файлы 0600 у пользователя `stand-panel`; адрес с токеном событий ещё в Secret `falco/falco-panel-output` |
| Доступность поиска | три копии сервиса поиска и три пира Qdrant на трёх машинах |
| Мак владельца | хост всех машин; на нём Ollama и файлы владельца |

## Допущения

- Сеть машин (`192.168.105.0/24`) враждебна, как публичный интернет. Мак с браузером в ней играет «внешний мир».
- machine-4 играет облачный балансировщик: вход доверенный, через него идут все пользователи. В сценах с неё же идёт атака «снаружи».
- Атакующий знает адреса машин и может слать им любые пакеты.
- Атакующий может получить shell в поде поиска, как будто нашёл дыру в нашем коде (сцена «заражённый под»).
- Атакующий с root на сервере k3s получает ключи всего кластера. От этого стенд не защищает, он показывает реакцию.

## Что остаётся открытым

- Root на машине стенда снимает её файрвол и тогда выходит в интернет и видит службы Мака на всех интерфейсах (например, AirPlay). localhost Мака при этом остаётся закрыт гипервизором. Проверено 18.11 со снятым файрволом. Поэтому сцена «заражённая машина» показывает реакцию: отрезать, пересоздать из чистой схемы, сменить ключи.
- Root на любом сервере k3s даёт ключи от всего кластера: все три машины кластера одновременно серверы.
- Узлы кластера доступны из сети машин по портам k3s и kubelet. Аутентификация есть, но поверхность шире, чем нужно. Закроет файрвол на входе каждой машины (план).
- Ключ API один на демо-клиента и хранится на Маке открытым файлом с правами 600.
- Между пирами Qdrant нет TLS: трафик между машинами шифрует WireGuard, но внутри машины он открытый.
- Вход на machine-4 один, его отказ стенд не переживает. В облаке на его месте был бы балансировщик провайдера.
- Тревоги Falco идут в панель по сети машин открытым HTTP, токен событий в адресе. Увидевший его может подделать событие в ленте панели, но только с адреса машины кластера.
- Токен панели читает описания всех подов кластера, а с ними и переменные окружения. Секретов там на стенде нет: ключи Qdrant подставляются из Secret (`secretKeyRef`), в описании пода видна только ссылка.
- Отказоустойчивость и защита проверены на одном ноутбуке. Это демонстрация механики, а не замер ёмкости.

## Как проверить самому

- `deploy/check.sh` прогоняет проверки кластера, входа, ключа API, Pod Security, песочницы машин и панели (права её учётной записи, срок токена, что видно с lima0).
- `deploy/scenes/` содержит сцены отказа. Сцены атак «снаружи» и «заражённый под» прогонялись 18.11 вручную, скрипты к ним: план.
- Разведка мер безопасности на 2026 год с источниками лежит в `docs/security/research-2026-11-18.md`.
